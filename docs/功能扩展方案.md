# 煤企安全监测系统 · 功能扩展方案

## 一、背景与现状

本系统已构建完成的基础架构：

- **鸿蒙三端**（Stage 模型，ArkTS）：企业端 / 智库端 / 监管端，各含综合总览、实时监测、预警管理、数据分析、用户管理、系统管理等模块；统一登录 + 验证码 + RBAC 角色鉴权 + 会话 Token。
- **后端**（Express + PostgreSQL + WebSocket）：覆盖传感器、预警、监管调度、审计、用户、矿井、分析、报告等模块；Redister 认证、IP/账号限流、RBAC 写接口权限。
- **数据链路**：MQTT（TLS + 账号认证，1983/8883）、UDP 网关（0.0.0.0:8890）双通道接入硬件端，可入库 + WebSocket 实时广播；模拟器 + 后端下行控制。

**核心结论**：硬件数据接入链路已打通，系统从"数据能收"阶段进入"数据要用好"阶段。本文档聚焦提升数据价值、增强业务闭环、强化三端差异化，并补齐工程与体验层能力。

## 二、功能挖掘总览

| 方向 | 说明 | 价值 | 改动量 |
|------|------|------|--------|
| 历史趋势分析 | 按时间聚合展示曲线、同比环比 | 三端通用，最高 | 中 |
| 数据来源溯源 | 每条数据标记来源通道/设备 | 可信度+审计 | 小 |
| 预警升级状态机 | 超时自动升级/上报 | 闭环增强 | 中 |
| 后端→硬件下行控制 | 指令下发到硬件端 | 策略闭环 | 中-大 |
| 多矿井对比看板 | 监管端集团级对比 | 监管差异化 | 中 |
| 报表模板引擎 | 智库端报告导出 | 智库差异化 | 中-大 |
| 数据归档任务 | 历史数据压缩聚合 | 工程保障 | 中 |
| 离线缓存/补传 | 弱网环境数据兜底 | 工业现场实用 | 大 |
| 巡检/工单打卡 | 复用用户/调度模块 | 操作闭环 | 中 |

## 三、推荐实施路径与详情

### 3.1 历史趋势分析页（推荐首选）
- **目的**：让实时数据有"历史纵深"，三端统一受益，改动可控。
- **实现**：
  - 后端新增 `GET /api/sensor/:id/history?from&to&interval`，按 interval（minute/hour/day）聚合。
  - 鸿蒙端以图表（折线/柱状）展示指定传感器趋势，支持时间范围选择。
- **复用**：`sensor_history` 表、`sensor.service` 查询基础、WebSocket 增量刷新。
- **验收**：选一传感器查看 24h 趋势曲线，数据随实时推送更新。

### 3.2 数据来源溯源（建议先做，为后续铺路）
- **目的**：区分 MQTT / UDP / 模拟器来源，审计可信度、支持问题设备追查。
- **实现**：
  - 在 `payload-parser.js` 解析结果中补充 `source`（mqtt / udp）与可选设备 ID。
  - 写入 `sensor_history` 时增加 `source`、`source_addr` 字段。
  - 鸿蒙端传感器详情页展示该条数据来源标识。
- **复用**：现成 `payload-parser`、`sensor_history` 表结构。
- **验收**：分别通过 MQTT 与 UDP 各发一条，详情页可区分来源。

### 3.3 预警升级状态机
- **目的**：预警长时间未处置自动升级（黄→橙→红→上报监管），形成闭环。
- **实现**：
  - `alert` 表扩展 `level`,`raised_count`,`escalated_at`。
  - 后端定时任务（可并入现有 backup/daemon）扫描超时未处理预警，按规则升级。
  - 升级后通过 WebSocket 推送，企业/监管端可见状态变化。
- **复用**：`alert.service`、`alert.routes`、备份 daemon 模式。
- **验收**：挂起一条黄色预警并触发超时，观察其自动升级并广播。

### 3.4 后端→硬件端下行控制（闭环关键）
- **目的**：发现异常后在监测系统直接对硬件端下发控制指令。
- **实现**：
  - 复用 UDP 8890 网关作为下行通道：后端向已注册硬件端地址发送控制帧。
  - 新增调度/控制 API，关联「触发指令→设备回复确认」状态。
- **风险**：需明确下行帧协议规范与设备地址注册表，涉及硬件端配合。
- **验收**：从系统下一条"停止"指令，硬件端收到并回执。

### 3.5 监管端多矿井对比看板
- **目的**：集团/安监视角，跨矿井横向比较安全态势。
- **实现**：
  - 聚合各 `mine_id` 的传感器均值、预警数、处置率、在线率。
  - 监管端新增"矿井对比" Tab，雷达/排行/地图展示。
- **复用**：`supervision` 模块、`mine` 表。
- **验收**：监管端可见多矿井指标排序与对比图。

### 3.6 智库端报表模板引擎 / 导出
- **目的**：科研机构一键生成分析报告并导出。
- **实现**：
  - 预置分析模板（安全态势、设备健康、数据统计），后端渲染。
  - 导出 PDF/Excel（Node 侧生成文件），鸿蒙端触发下载。
- **复用**：`analysis` 模块、`report` 模块。
- **验收**：选模板生成报告并可导出。

### 3.7 数据归档任务
- **目的**：控制 `sensor_history` 增长速度，保障性能与存储。
- **实现**：
  - 定时任务将超过 N 天的原始明细聚合成小时/日维度归档表，原始数据可选清理。
  - 趋势查询优先命中归档表。复用现有 backup 调度模式。
- **验收**：历史数据被聚合，趋势查询仍正确且更快。

### 3.8 离线缓存 / 断点补传（长期）
- **目的**：井下弱网环境，硬件端数据不因断连丢失。
- **考虑**：涉及硬件端与网关两侧改造与协议约定，建议作为二期独立立项。

## 四、优先级建议

| 优先级 | 事项 | 理由 |
|--------|------|------|
| P0 | 历史趋势分析、数据来源溯源 | 复用度高、改动小、三端通用，为后续铺路 |
| P1 | 预警升级状态机、多矿井对比看板 | 闭环增强与监管差异化价值高 |
| P2 | 报表导出、数据归档 | 智库差异化与工程保障 |
| P3 | 后端下行控制、离线补传 | 依赖硬件端配合，独立立项 |

---

## 五、验收与工程约束

- 所有改动遵循：后端在 `prj/backend` 运行、鸿蒙端请求走 Token 鉴权、写接口受 RBAC 角色约束。
- 新增接口遵循错误码约定（2xx 视为成功），新增模块挂到 `src/app.js` 路由与 `BackendApi.ets`。
- 数据接入统一走 `payload-parser` 与既有网关，保证来源可追溯。
- 部署产物需同步到 `qianduanyemian` / `qiandaudeepin` 及后端部署脚本。
